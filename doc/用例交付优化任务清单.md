# 请求用例交付优化任务清单

> 本文是评审清单，不代表已经确认开发。
> 当前重点是请求用例从创建、保存、执行、复用到导出和导入的完整交付链路。

## 0. 术语说明

本文所说的“请求用例交付”，是指把用户选定的接口和请求用例打包，交给另一个项目导入后继续打开、修改和发送。交付包会自动带上请求用例所依赖的父接口定义，避免导入后出现没有归属接口的请求用例。

请求用例交付不等于测试执行或结果报告：不包含响应历史、断言、预期响应、通过/失败状态和测试报告。项目完整备份仍单独用于项目级恢复，两者的入口和范围分开。

## 1. 当前事实

### 1.1 请求用例当前保存的内容

`RequestCaseDto` 目前通过 `EntryType` 区分 `quick-request`、`http-interface` 和 `http-case`。`http-case` 主要保存：

- 所属接口 `ParentId`
- 请求快照 `RequestSnapshot`
- 请求名称、目录、标签和说明
- 方法、URL、Params、Path 参数、Headers、Body 等请求配置

当前 DTO 没有独立的预期响应、断言、通过/失败结果、执行记录或版本信息；这与本项目只保存调试请求参数的范围一致。

结论：不需要预期响应、断言、通过/失败状态或测试报告；只做接口请求工具，保存请求用例即可。

### 1.2 当前保存行为

- 工作区只有一个通用“保存”入口，但实际行为依赖当前标签类型和是否存在 `EditingCaseId`。
- 接口模式点击保存，保存接口定义。
- 接口模式点击保存请求用例，会先隐式保存接口，再保存请求用例。
- 已加载请求用例时点击保存，会更新当前请求用例。
- 快捷请求保存需要单独弹窗；快捷请求还可以转为 HTTP 接口后再次保存。
- 当前请求用例的加载、改名、复制和删除仍需要在接口目录下完成；不采用独立的请求用例抽屉作为主要入口。

主要实现位置：

- [`ProjectRequestWorkflowViewModel.cs`](../src/ApixPress.App/ViewModels/ProjectRequestWorkflowViewModel.cs)
- [`UseCasesPanelViewModel.cs`](../src/ApixPress.App/ViewModels/UseCasesPanelViewModel.cs)
- [`ProjectWorkspaceCatalogViewModel.cs`](../src/ApixPress.App/ViewModels/ProjectWorkspaceCatalogViewModel.cs)
- [`RequestCaseDto.cs`](../src/ApixPress.Core/Models/DTOs/RequestCaseDto.cs)
- [`RequestSnapshotDto.cs`](../src/ApixPress.Core/Models/DTOs/RequestSnapshotDto.cs)

### 1.3 当前交付行为

- 项目数据包目前包含接口和请求用例，但导出请求只携带项目和目标文件路径，不能选择具体请求用例或交付范围。
- 导出服务会读取当前项目全部接口和用例，并直接写入目标文件。
- 导入时先写入接口文档和接口节点，再同步用例；接口和用例并非一个完整事务。
- 请求用例父接口的导入关联依赖方法和路径生成的键，接口发生重命名、来源变化或重复时，交付稳定性需要继续确认。
- 当前项目数据导出设计中的 HTML / Markdown 面向接口文档，同时附带请求用例示例；可恢复的请求用例仍由交付包负责。

### 1.4 已确认的 Apifox 参考规则与本项目取舍

根据本轮截图，以下规则作为后续评审的已确认参考，不再作为开放问题：

- URL、Params 等请求字段可以引用环境变量，例如 `{{apiKey}}`。
- Body 不支持引用参数，本轮不要求在 Body 编辑器中增加环境变量引用能力。
- 环境变量在环境管理页面右侧的本地值列直接编辑，不增加必须跳转的二级编辑表单。
- 保存请求用例位于“保存”按钮的下拉菜单中，不需要长期占用主操作区。
- Apifox 保存弹窗虽然提供“调试用例”和“测试用例”选项，但本项目统一使用“请求用例”，不做测试用例体系。
- 请求用例只用于保存日常测试所需的请求参数和请求配置；响应继续进入请求历史，不写入请求用例。
- 保存请求用例时只需要填写用例名称，不增加断言、预期状态码或测试结果字段。
- 请求用例作为接口的下一级节点显示，接口树默认收缩；接口节点显示请求用例数量。

### 1.5 已确认的产品决策

- **名称**：界面和文档使用“请求用例”。
- **范围**：请求用例只保存请求配置，不包含断言、预期响应、测试结果或测试报告。
- **交付**：同时保留项目完整备份，以及按接口和请求用例选择的独立交付包。
- **交付包环境**：请求用例交付包包含前置 URL、环境名称、变量名和变量值；环境仍是项目级全局上下文。
- **文档示例**：HTML / Markdown 文档附带请求用例示例，供阅读和复制参考；请求用例的可恢复导入仍使用交付包。
- **快捷请求**：继续作为独立对象保留，并支持转换为 HTTP 接口。
- **保存**：保存请求用例时自动保存未保存的父接口，并明确提示接口和请求用例均已保存。

## 2. 先确认产品定义

以下任务依赖第一个判断。没有这个判断，后续界面和导出设计容易再次混用概念。

### UC-01 确认请求用例范围

- **优先级**：P0
- **已确认结论**：本项目只做“请求用例”，不做“测试用例”。请求用例用于保存平常调试接口时的请求参数和请求配置。
- **要解决的问题**：当前界面和文档使用“测试用例”称呼，容易让用户期待断言、预期结果和测试报告能力。
- **任务内容**：
  - 统一使用“请求用例”文案。
  - 保存方法、路径、Params、Path 参数、Headers、Body 和相关请求配置。
  - 不增加断言、预期响应、测试结果和测试报告字段。
  - 响应结果继续由请求历史保存和查看。
- **建议验收**：用户可以保存一组日常请求参数，重新加载后直接发送；界面不出现“测试用例”入口或测试结果承诺。


### UC-02 明确接口、请求用例、快捷请求的边界

- **优先级**：P0
- **要解决的问题**：接口、请求用例和快捷请求共用目录和请求编辑器，但保存、加载和转化规则不同，用户需要依靠当前标签状态猜测操作结果。
- **已确认结论**：快捷请求继续作为独立对象保留，并支持转换为 HTTP 接口；请求用例不替代快捷请求。
- **任务内容**：补一张对象关系和生命周期表，明确创建、打开、另存、复制、转化、删除、导出和导入规则。
- **建议验收**：任意页面都能回答“我现在编辑的是什么”“保存后会更新什么”“交付时会带走什么”。

## 3. 保存与复用链路

### UC-03 拆分保存动作和保存结果

- **优先级**：P0
- **要解决的问题**：同一个“保存”按钮在接口模式、请求用例模式和快捷请求模式下含义不同；保存请求用例还会联动保存父接口。
- **已确认结论**：采用方案 A。保存请求用例时自动保存未保存的父接口，并提示“接口和请求用例已保存”。
- **任务内容**：参考 Apifox，将“保存请求用例”放在“保存”按钮下拉菜单中，同时明确：
  - 主按钮保存接口定义或当前已加载对象。
  - 下拉菜单提供“保存为请求用例”。
  - 保存请求用例弹窗只填写请求用例名称。
  - 快捷请求保存和快捷请求转接口仍保持独立动作。
- **建议验收**：每个保存动作都有唯一目标对象；保存请求用例时接口和请求用例的保存结果可分别确认。

### UC-04 建立清晰的用例上下文和脏状态

- **优先级**：P0
- **要解决的问题**：当前用例虽然有“接口模式 / 用例模式”提示，但用户仍难以确认当前修改的是接口还是用例，也不容易知道修改是否已经写入。
- **任务内容**：
  - 在编辑区固定显示接口名称、用例名称和当前模式。
  - 显示“已保存 / 有未保存修改”状态。
  - 切换接口、用例或标签时，对未保存修改给出处理选项。
  - 保存成功后明确刷新目录、用例计数和更新时间。
- **建议验收**：切换和关闭前不会静默丢弃用例修改；用户能从界面判断持久化状态。

### UC-05 调整接口树中的请求用例层级

- **优先级**：P1
- **参考结论**：请求用例放在左侧接口节点的下一级，接口树默认收缩；接口节点显示请求用例数量。
- **要解决的问题**：当前用例抽屉承担了过多管理职责，接口树和用例之间的层级关系不够直接。
- **任务内容**：
  - 接口节点显示请求用例数量。
  - 默认收缩接口下的请求用例节点，展开后显示请求用例列表。
  - 请求用例节点显示名称和必要的状态信息。
  - 保留加载、改名、复制、删除和另存为新用例。
  - 用例较多时保留虚拟化和稳定排序。
- **建议验收**：用户从接口节点展开即可找到用例，不需要额外打开独立抽屉；接口树收缩状态符合默认行为。

### UC-06 定义“发送后保存”的关系

- **优先级**：P1
- **要解决的问题**：发送请求、保存请求配置和保存请求用例是三个不同动作，当前界面需要明确响应不会成为请求用例的一部分。
- **已确认结论**：请求用例只保存请求配置；响应不写入请求用例，统一进入请求历史。
- **任务内容**：
  - 保存请求用例后保留当前请求历史记录。
  - 加载请求用例只回填请求编辑区，不伪造历史响应。
  - 导出请求用例时只导出请求配置，不附带响应正文。
- **建议验收**：发送、保存、历史和请求用例之间的职责清晰，重新加载请求用例后可以直接发送。

## 4. 环境配置与请求引用

### ENV-01 环境变量右侧直接编辑

- **优先级**：P1
- **参考结论**：环境变量在右侧本地值列直接编辑，环境仍是项目级全局上下文。
- **任务内容**：
  - 保留环境列表、当前环境和前置 URL 区域。
  - 本地值列支持直接编辑、添加和删除。
  - 编辑后提供统一保存和保存并关闭。
  - 不在接口请求编辑区重复展示环境变量管理表单。
- **建议验收**：用户可以在一个环境页面完成变量维护，不需要为每个变量打开单独弹窗。

### ENV-02 明确变量引用边界

- **优先级**：P1
- **参考结论**：URL、Params 等请求字段可以引用环境变量；Body 不支持引用参数，本轮不增加该能力。
- **任务内容**：
  - 统一变量语法和未解析变量提示。
  - 在发送前或实际请求页签中显示变量解析后的结果。
  - 保证环境切换只影响支持变量引用的请求字段。
  - 不对 JSON Body 增加变量选择器、插值提示或自动替换逻辑。
- **建议验收**：变量解析行为在 URL、Params、Headers 等支持范围内一致；Body 保持普通编辑行为。

## 5. 请求用例交付包

### UC-07 同时支持项目备份和请求用例交付

- **优先级**：P0
- **已确认结论**：采用方案 C。项目完整备份和请求用例交付保留两个入口、两套范围。
- **交付含义**：请求用例交付包面向跨项目复用，包含用户选定的请求用例及其父接口定义；导入后可以直接加载和发送。它不承担项目完整恢复，也不携带响应历史或测试结果。
- **要解决的问题**：当前项目数据包承担迁移备份职责，但用户想交付请求用例时无法只选择目标内容，也无法快速知道交付内容。
- **任务内容**：
  - 项目备份保留当前项目完整恢复用途。
  - 增加独立的“交付请求用例”入口，至少支持：
    - 选择一个或多个接口。
    - 选择接口下的一个或多个请求用例。
    - 自动带上请求用例依赖的接口定义。
    - 包含项目级环境配置：前置 URL、环境名称、变量名和变量值；不在请求 URL 上重复绑定全局环境。
    - 导出前显示接口数、请求用例数和其他附带内容。
- **建议验收**：项目备份可以完整恢复；请求用例交付包只包含用户选择的内容，同时不会产生缺少父接口的孤儿请求用例。

### UC-08 设计可稳定导入的交付包结构

- **优先级**：P0
- **要解决的问题**：当前导入关联依赖方法和路径键，无法充分表达接口与请求用例之间的稳定关系。
- **任务内容**：为请求用例交付包定义稳定的接口标识、请求用例父子关系、格式版本和来源信息；导入时按包内关系恢复，不依赖导入后的数据库 ID。
- **建议验收**：接口改名、跨项目导入、多个来源存在相同方法和路径时，仍能正确恢复请求用例归属。

### UC-09 增加导入预览、冲突处理和失败回滚

- **优先级**：P0
- **要解决的问题**：当前预览主要围绕接口冲突；导入写入接口后再写请求用例，部分失败可能留下不完整数据。
- **任务内容**：
  - 预览接口、请求用例、环境和冲突数量。
  - 分别显示新增、更新、跳过和孤儿项。
  - 允许按接口或请求用例选择覆盖、跳过或另存。
  - 整个导入过程成功后一次提交，失败或取消时回滚本次导入。
- **建议验收**：导入失败后项目中不会出现只导入接口、请求用例缺失或父子关系断开的半成品。

### UC-10 明确文档导出的请求用例范围

- **优先级**：P1
- **要解决的问题**：当前 HTML / Markdown 设计只面向接口文档，用户无法判断文档交付是否包含可复用请求用例。
- **已确认方向**：HTML / Markdown 附带请求用例示例，供阅读和复制参考；请求用例的可恢复导入仍由交付包承担。
- **建议验收**：不同导出格式在入口、范围说明和结果统计上不会混淆。

## 6. 交付验证

### UC-11 建立完整的请求用例交付验收链路

- **优先级**：P1
- **任务内容**：围绕真实 TestApi 流程验证：

```text
导入接口
  → 编辑请求
  → 发送请求
  → 保存为请求用例
  → 关闭并重新打开项目
  → 加载请求用例
  → 修改并保存
  → 导出交付包
  → 在另一项目导入
  → 核对接口、请求用例、父子关系和请求快照
```

- **建议验收**：流程中每个阶段都有可观察结果；导入后的请求用例可以直接加载并发送，不需要手工修复父接口或路径。

### UC-12 统一请求用例交付相关的界面密度和文案

- **优先级**：P2
- **任务内容**：在对象和流程确认后再调整视觉层：
  - 请求用例列表减少大卡片空白，提高列表密度。
  - 保存区使用明确的对象名称和动作名称。
  - 响应区显示本次请求是否已保存为请求用例。
  - 导入导出页面显示“备份”“请求用例交付包”“文档”的差异。
  - 当前环境只作为全局上下文显示，不在每个请求卡片中重复展示。
- **建议验收**：用户不阅读帮助文案，也能区分接口、快捷请求、请求用例、备份和交付包。

## 7. 明确不纳入本清单

以下内容按你的反馈不作为本轮任务：

- 针对 `/models`、`model` 字段或其他大模型接口的专用能力。
- 将全局环境 `litellm` 绑定到每个接口 URL 或在请求区域重复展示环境关系。
- 在 Body 编辑器中支持环境变量引用或参数插值。
- 测试用例、断言、预期响应、测试结果和测试报告体系。
- API Key 默认隐藏、脱敏或改变当前显示方式。

## 8. 已确认的补充范围

- 请求用例交付包包含前置 URL、环境名称、变量名和变量值。
- HTML / Markdown 文档包含请求用例示例，但不替代可恢复的请求用例交付包。
- 快捷请求继续作为独立对象保留，并支持转换为 HTTP 接口。

## 9. 建议评审顺序

建议先判断：

1. `UC-01`：请求用例的保存字段和响应归属。
2. `UC-02`：接口、请求用例、快捷请求的边界。
3. `UC-05`：接口树下一级请求用例节点和默认收缩规则。
4. `UC-07`：项目备份和请求用例交付包的范围差异。
5. `UC-08` 与 `UC-09`：交付包的稳定关联和导入回滚要求。
6. 再决定 `UC-03`、`UC-04`、`UC-06` 和 `ENV-01`、`ENV-02` 的实现范围。

## 10. 新会话开发交接

新会话开始前先阅读本文和 `TASK.md`。以下内容已经确认，可以作为后续需求和设计的基线：

- 产品对象统一称为“请求用例”，只保存日常请求配置：方法、URL、Params、Path 参数、Headers、Body 及其他请求配置。
- 请求用例不包含断言、预期响应、测试结果、测试报告或响应历史；响应进入请求历史。
